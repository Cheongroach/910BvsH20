# 项目过程：从一个模糊问题到可复算实验

这份文档是完整对话的易读版。它不按每条消息排列，而是按“问题如何变化、实验如何纠错、结论如何收敛”组织。

需要逐轮审计时，请看 [完整脱敏对话](CONVERSATION_HISTORY.md)。

## 1. 最初的问题

最初需求是比较 H20 与 Ascend 910B4 在 Qwen 小模型推理中的性能：

- 模型范围约 2B–14B；
- 输入长度为 1K–2K token；
- 任务包含单分数判断、答案提取和较长生成；
- 尽量打开常见优化，追求吞吐；
- 同时保留 baseline 和独立消融；
- 最终形成完整报告。

这个问题一开始有两个模糊点：

1. “性能”可能指吞吐，也可能指首 token、逐 token 或尾延迟；
2. “打开更多优化”不一定更快，需要单独测每项优化。

因此项目后来被拆成吞吐实验和请求级延迟实验两部分。

## 2. 首轮：建立吞吐矩阵

首轮先固定公平比较条件：

- 两端使用相同模型和相同数据；
- 输入严格构造为 1,024 或 2,048 token；
- 输出固定为 1、64 或 128 token；
- 使用相同随机种子和确定性采样；
- 普通测试使用不同前缀，避免意外命中 prefix cache；
- 模型文件和数据记录 revision 与 SHA-256。

主矩阵最终包含 480 种唯一配置：

```text
2 硬件 × 5 模型 × 2 配置
× 2 输入长度 × 3 输出长度 × 4 batch
```

4B 模型还增加了 graph、compile、chunked prefill、prefix cache、FP8 和 MTP 的独立消融。

### 这一阶段遇到的问题

实验并不是一次跑通的。主要问题包括：

- 两端 vLLM 和 PyTorch 版本不同；
- 910B4 环境缺少或无法加载部分自定义算子；
- CANN 库路径和自定义算子目录权限不正确；
- Ascend KV block size 与默认配置不兼容；
- H20 侧 Transformers 返回格式变化；
- 旧引擎进程残留导致显存占用；
- 模型下载路径和代理速度影响准备时间。

这些问题逐项修复后，才开始记录可比较性能。失败日志没有被填成零吞吐。

### 首轮得到的认识

- H20 的 2B/4B 长输出生成优势明显；
- 910B4 在部分短输出判断中更快；
- Graph/compile 对 4B 长输出收益明显；
- Chunked prefill 在这组固定长度负载中没有提高吞吐；
- MTP 在所测 4B 场景中没有稳定收益；
- Prefix cache 只在真实存在共享前缀时有意义；
- “全部优化一起打开”不保证比最佳单项更快。

首轮最终完成 480/480 格和 1,326 次底层测量。

## 3. 第二轮：补齐用户真正感受到的延迟

只看吞吐不能回答“用户要等多久”，因此需求扩展为：

- 离线 TTFT；
- TPOT；
- 精确可观察 ITL；
- 在线流式 E2E P95/P99；
- 闭环并发；
- Poisson 开放到达。

模型也扩展到 Qwen3.5/3.6/3.8-27B。同规模 27B 对照用于判断异常是否只属于某一个 checkpoint。

### 在线测试的一次重要纠错

早期在线实验使用固定端口。后来出现请求收到“模型不存在”的响应，说明请求可能误连到其他实验服务。

修正方式是：

- 每个服务使用独立端口；
- 请求前核对服务返回的模型名；
- 旧固定端口数据保留为历史记录，但不进入正式结论；
- 正式矩阵只选择独立端口协议的数据。

这是项目中最重要的测量纠错之一。如果不做这一步，P95 和吞吐数字可能看起来正常，但比较对象实际上错误。

### 如何处理逐 token 时间

流式服务有时一次返回多个 token。项目没有把一个 chunk 内的多个 token 人为摊开，而是：

- 每个请求保留完整 token-arrival 时间数组；
- TPOT 按首尾 token 计算；
- ITL 只使用前后 chunk 都恰好为单 token 的间隔；
- 单独记录精确 ITL 覆盖率。

这样做牺牲了一部分样本量，但避免制造不存在的时间戳。

## 4. 27B 高并发异常

第二轮最值得继续研究的现象来自 910B4 的 27B 组合配置。

固定为 1K 输入、128 输出：

- 并发 8 时约 97–98 output tok/s，E2E P95 约 10 秒；
- 并发 32 时约 49 output tok/s，E2E P95 约 102 秒。

Qwen3.5、Qwen3.6 和 Qwen3.8-27B 都出现相似现象。补跑任务只补缺失格，不把补跑当作独立重复实验。

项目最终没有宣称根因。服务初始化日志提供了 KV cache 和估计并发线索，但缺少退化阶段的完整调度、抢占和 profiler 证据。结论因此限定为：

> 所测 910B4 部署栈在 27B、combo、并发 32 下出现退化。

## 5. 最终证据规模

| 项目 | 结果 |
|---|---:|
| 吞吐主矩阵 | 480/480 格 |
| 底层吞吐测量 | 1,326 次 |
| 请求级延迟矩阵 | 728/728 格 |
| 正式延迟请求 | 58,240 个，错误 0 |
| 跨硬件输入配对 | 23,520 对 |
| 输入哈希不一致 | 0 |

这些数字分别代表配置覆盖、底层测量和请求样本，不能互相替代。

## 6. 结论如何变得更克制

项目早期目标是比较“哪张卡更快”。最终结论变成按任务和指标选择：

- 2B/4B 长输出生成：H20 优势明确；
- 9B/14B：吞吐、TTFT 和 E2E 可能给出不同选择；
- 14B 短输出：910B4 在部分配置下更快；
- 27B 高并发：所测 910B4 栈应先降低并发复验；
- 所有结论都绑定具体模型、输入输出长度、配置和并发。

这比一个统一硬件排名更接近真实部署决策。

## 7. 项目如何对外发布

公开仓库保留：

- 可移植 benchmark 代码；
- 固定模型清单与公开工作负载；
- 聚合 CSV；
- 图表；
- 数据校验和重绘脚本；
- 方法、结论、STAR 和脱敏对话。

没有公开：

- 体积过大的逐请求原始轨迹；
- 含环境元数据的调度日志；
- 内部 URL、资源名、用户名和任务 ID；
- 系统或开发者指令。

完整对话只包含用户可见的 User/Assistant 消息，并对内部标识做了替换。
