# STAR project narrative

## Project name

**HeteroInferLab: H20 vs Ascend 910B4 Inference Benchmark**

## Situation

团队需要判断 NVIDIA H20 与 Ascend 910B4 在真实大模型推理部署中的性能差异。
只看芯片峰值算力无法回答实际吞吐、首 token 延迟、生成阶段延迟和高并发尾延迟，
而且两套 vLLM 后端、图执行能力与优化支持并不完全一致。

## Task

设计一套可复现、可审计的异构推理基准，覆盖 2B 到 27B 模型、1K/2K
输入、不同输出长度、批大小、并发和到达模式；同时区分基线、组合优化和独立
消融，避免把输入不一致、缓存命中或首次编译误判为硬件收益。

## Action

1. 构建了固定 token 形状的吞吐脚本和异步/HTTP 流式延迟脚本，统一采集
   requests/s、output tokens/s、TTFT、TPOT、精确可观测 ITL 和 E2E 尾延迟。
2. 将主实验拆成 `2 x 5 x 2 x 2 x 3 x 4 = 480` 个唯一配置格，
   并额外测试 graph/compile、chunked prefill、prefix cache、FP8 和 MTP。
3. 固定模型 revision、数据集哈希、随机种子和输出长度；为普通请求注入唯一
   前缀，并通过输入哈希验证跨硬件请求严格配对。
4. 增加完整形状 warmup、隔离 HTTP 端口、SSE token chunk 校验、矩阵覆盖
   检查和错误检查，最终保留可公开复算的聚合 CSV 与绘图脚本。
5. 对 27B 高并发异常做跨 Qwen3.5/3.6/3.8 的同规模复测，将结论限制为
   “部署栈出现并发回退”，没有在缺少 profiler 证据时归因到芯片。

## Result

- 完成 480/480 个吞吐配置格和 1,326 次有效吞吐测量。
- 完成 728/728 个延迟配置格，共 58,240 个成功请求，正式请求错误为 0。
- 验证 23,520 对跨硬件输入，哈希不一致为 0。
- 在 1K 输入、128 输出、在线闭环并发 32 的组合优化场景，H20 对
  Qwen3.5-2B/4B 的生成吞吐分别约为 910B4 的 2.03x/1.87x。
- 定位到 910B4 的 27B 组合配置从并发 8 提升到 32 时，吞吐约从
  97-98 tok/s 降至约 49 tok/s，E2E P95 从约 10.3 秒升至约 102 秒。

## What “480 cells” means

“格”是一个唯一实验配置，而不是一条请求，也不是一个训练或调度任务：

```text
硬件 x 模型 x 配置 x 输入长度 x 输出长度 x batch
```

例如：

```text
H20 x Qwen3.5-4B x combo x 1024 input x 128 output x batch 32
```

这就是一个格。一个调度任务可以连续执行多个格，一个格也可以包含多条请求和
多次重复测量。因此“480 格”表达的是实验设计覆盖度，“58,240 requests”
表达的是请求样本量，两者不能互换。

## Resume bullet

> 设计并实现 H20/Ascend 910B4 单卡大模型推理基准，覆盖 2B-27B 模型、
> 480 个吞吐配置和 728 个延迟配置；通过固定 token 形状、跨硬件输入哈希
> 配对、完整 warmup 与独立消融保证可比性，完成 58,240 个零错误请求，
> 量化 H20 在典型 2B/4B 生成场景的 2.03x/1.87x 吞吐优势，并定位
> 910B4 27B 高并发下约 50% 吞吐回退与 10x P95 放大。

面试中应补充两个边界：数字代表完整软硬件部署，不是芯片峰值比较；27B
异常是实验现象，尚未通过 profiler 证明根因。
