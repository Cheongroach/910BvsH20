# STAR 与简历表达

## 这个项目真正证明了什么

这个项目的价值不只是得到“H20 比 910B4 快多少”的数字，而是展示了一套完整的 AI Infra 工作方法：

1. 把模糊的硬件比较问题拆成可控实验矩阵；
2. 同时测吞吐、首 token、逐 token 和尾延迟；
3. 用独立消融区分优化收益；
4. 发现并修正端口串扰、输入不一致等测量问题；
5. 对无法证明的根因保持克制；
6. 发布可复算的聚合数据和校验脚本。

这些能力比某一个倍率更适合作为简历重点。

## STAR 是什么

STAR 用四部分讲清一个项目：

| 部分 | 要回答的问题 |
|---|---|
| Situation | 为什么要做？原问题是什么？ |
| Task | 你负责交付什么？难点是什么？ |
| Action | 你具体做了哪些关键工作？ |
| Result | 结果如何？有哪些可验证数字？ |

重点应放在 Action 和 Result。Situation 不需要写成行业背景介绍。

## 本项目的 STAR

### Situation

团队需要判断 NVIDIA H20 与 Ascend 910B4 在真实大模型推理中的适用场景。芯片峰值算力不能直接回答部署问题，因为两端使用不同的运行时、编译器、算子和 vLLM 后端，而且吞吐高不代表首 token 或 P95 更好。

### Task

我的任务是设计一套可复现、可审计的单卡异构推理基准，覆盖：

- 2B 到 27B 的 Qwen 模型；
- 1K/2K 输入；
- 判断、短答案和长生成三种计算形状；
- 不同 batch、并发和请求到达模式；
- baseline、组合优化和独立消融。

核心要求是保证两端输入可比，并把实验现象与机制推断分开。

### Action

我完成了五类关键工作。

第一，构建两套基准：

- 固定 token 形状的离线吞吐测试；
- 异步引擎和 OpenAI-compatible SSE 的请求级延迟测试。

第二，把主吞吐实验拆成 480 个唯一配置格：

```text
2 硬件 × 5 模型 × 2 配置
× 2 输入长度 × 3 输出长度 × 4 batch
```

第三，控制实验变量：

- 固定模型 revision 和文件 SHA-256；
- 固定数据集、随机种子和输出长度；
- 构造精确的 1,024/2,048-token 输入；
- 用输入哈希验证跨硬件请求配对；
- 用唯一前缀避免普通测试意外命中 prefix cache；
- 用同形状预热减少首次编译污染。

第四，独立测试 graph/compile、chunked prefill、prefix cache、FP8 和 MTP，而不是只比较“全部打开”和“全部关闭”。

第五，建立数据质量门禁：

- 校验输出 token 数和请求错误；
- 检查完整矩阵；
- 隔离在线服务端口，修正早期端口串扰；
- 记录精确可观察 ITL 覆盖率；
- 对 27B 退化跨 Qwen3.5/3.6/3.8 做同规模复测。

### Result

- 完成 `480/480` 个吞吐配置格和 1,326 次底层吞吐测量；
- 完成 `728/728` 个延迟配置格，共 58,240 个成功请求；
- 完成 23,520 对跨硬件输入配对，输入哈希不一致为 0；
- 在 1K→128、combo、在线并发 32 下，H20 的 Qwen3.5-2B/4B 生成吞吐分别为 910B4 的 2.03x/1.87x；
- 发现所测 910B4 栈上的 27B 高并发退化：并发 8→32 后吞吐约减半，E2E P95 从约 10 秒升至约 102 秒；
- 发布基准代码、聚合 CSV、图表和可执行校验脚本。

最后一项异常只写成部署栈观察，没有在缺少 profiler 证据时归因到芯片机制。

## “480 格”在面试中怎么解释

一格是一种唯一配置，不是一条请求：

```text
H20 × Qwen3.5-4B × combo
× 1,024 输入 × 128 输出 × batch 32
```

480 来自：

```text
2 × 5 × 2 × 2 × 3 × 4 = 480
```

一个调度任务可以运行很多格；一格也会包含多条请求。因此：

- 480 表示实验设计覆盖；
- 1,326 表示包含重复和消融后的吞吐测量数量；
- 58,240 表示请求级延迟实验中的正式请求数量。

这三个数字不能互换。

## 90 秒面试讲法

> 我做这个项目是因为只看 H20 和 910B4 的峰值算力，无法回答真实推理部署该怎么选。我把问题拆成了两套实验：一套测饱和吞吐，一套测请求级 TTFT、TPOT 和 E2E P95。
>
> 吞吐主矩阵有 480 种唯一配置，覆盖两种硬件、五个模型、两种输入长度、三种输出长度和四档 batch。我固定模型文件、数据集、随机种子和 token 形状，并用输入哈希保证跨硬件请求一致。4B 上还独立做了 graph、chunked prefill、prefix cache、FP8 和 MTP 消融。
>
> 最后完成了 1,326 次吞吐测量和 58,240 个请求级延迟样本。结果不是简单的单边胜负：2B/4B 长输出 H20 明显更快，但 9B/14B 的短输出和首 token 指标中 910B4 有部分优势。更重要的是，我在三套 27B checkpoint 上复现了 910B4 部署栈并发从 8 提到 32 后吞吐减半、P95 放大约 10 倍的现象。由于没有 profiler 证据，我只把它表述为部署栈退化，没有直接归因到芯片。

## 面试官可能追问什么

### 为什么不能只看 tokens/s？

因为 tokens/s 是系统总产能。用户体验还取决于 TTFT 和 E2E P95。高并发可能提高吞吐，也可能增加排队，让首 token 和尾延迟变差。

### 如何保证两端输入相同？

模型文件和数据集有固定 revision/SHA-256；输入经过 tokenizer 后严格构造为固定长度；跨硬件闭环请求用输入 token 哈希配对，23,520 对没有不一致。

### 为什么要做独立消融？

如果同时打开 graph、chunked prefill 和其他优化，只能知道组合结果，不能知道收益来自哪一项。实际结果也证明优化不能简单叠加：4B 中 graph 明显增益，而 chunked prefill 在该固定长度负载下没有提高吞吐。

### 27B 退化的根因是什么？

当前不知道。可以确认的是三套同规模 checkpoint 都出现相似退化，因此单一模型版本不是强解释。要进一步定位，需要采集调度、KV cache、显存和 profiler 时间线。

### 为什么两端软件不同还要比较？

因为部署决策面对的就是完整可用栈，而不是抽象芯片。报告明确把结论限定为完整部署比较；如果要做纯芯片研究，需要更严格地对齐软件和算子实现。

## 不要在简历或面试中这样说

- “证明 H20 全面快于 910B4。”
- “证明 910B4 的 KV cache 导致 27B 退化。”
- “58,240 个请求证明生产 SLA。”
- “固定 128-token 生成证明回答质量。”
- “输入哈希一致证明输出完全一致。”

这些说法都超过了现有证据。
