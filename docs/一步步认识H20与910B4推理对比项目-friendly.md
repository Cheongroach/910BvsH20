# 一步步认识 H20 与 910B4 推理对比项目

这不是硬件规格表，也不是跑分排行榜。

它只做一件事：让已经知道 token、embedding、Attention 和大模型推理基本过程的读者，逐层看懂这个项目到底比较了什么，以及为什么驱动、运行时、算子和调度器都会改变结果。

请按顺序阅读。每一步只增加一个概念。读完一步后，先回答末尾的问题；答不出来就停在这里，不要继续记后面的版本号。

全文分为 10 个阶段。本文不会重复 embedding、位置编码或 Attention 的基础知识。

实验数字来自 2026-10-19 已完成的历史实验，不是你当前机器刚刚测出的结果。

---

## 第一阶段：先确定比较对象

### 第 1 步：项目比较两套单卡推理部署

项目使用两种加速卡：

- NVIDIA H20；
- Ascend 910B4-64G。

两端都是单卡运行，`tensor_parallel_size=1`。模型没有被拆到多张卡上。

只记住：**这是单卡 H20 与单卡 910B4 的部署对比。**

停下来回答：本项目有没有比较两卡或八卡推理？

---

### 第 2 步：一张加速卡不能单独运行模型

模型请求不会从 Python 直接跳进芯片。中间至少经过推理引擎、框架、设备运行时、驱动和设备算子。

本项目真正运行的是两条完整路径：

```text
请求
  ↓
vLLM
  ↓
PyTorch + CUDA 软件栈
  ↓
H20
```

```text
请求
  ↓
vLLM + vLLM-Ascend
  ↓
PyTorch + torch-npu + CANN 软件栈
  ↓
910B4
```

只记住：**硬件只是执行栈的最后一层。**

停下来回答：同一张卡换一个 vLLM 后端，性能是否可能变化？

---

### 第 3 步：项目不能给出“纯芯片”排名

两端的软件版本和后端实现不同。即使输入、模型和并发相同，执行图、算子实现和调度路径仍然不同。

因此，项目能回答：

> 在本次两套完整环境中，哪个部署在指定负载下更快？

项目不能单独回答：

> 如果两块芯片使用完全等价的软件，哪块芯片本体更强？

只记住：**结果属于“硬件 + 软件栈”，不是脱离软件的芯片峰值比较。**

停下来回答：H20 比 910B4 快 2 倍时，能否把全部差距归因于晶体管或计算单元？

---

### 第 4 步：公平比较从固定工作负载开始

同一条请求在两端使用相同的模型文件、输入 token 数和输出 token 数。正式闭环请求还按输入哈希配对。

但是，“输入相同”只控制了工作负载，没有让两端的软件实现变成同一个实现。

只记住：**相同输入是公平比较的必要条件，但不是纯硬件比较的充分条件。**

停下来回答：输入哈希一致能否证明两端调用了相同的设备 kernel？

---

你现在应该能说出：

```text
本项目比较两套完整的单卡推理部署，
不是只比较 H20 与 910B4 的理论硬件参数。
```

如果仍把结果理解成“芯片跑分”，请不要继续。

## 第二阶段：先认识硬件层

### 第 5 步：H20 是 NVIDIA GPU

H20 属于 NVIDIA GPU。模型计算最终被编译或选择成 CUDA 设备 kernel，由 GPU 上的计算单元执行。

H20 中适合矩阵计算的硬件单元会被 GEMM、Attention、GDN 等 kernel 使用。但本项目没有采集 kernel 级 profiler，因此不知道每个 kernel 实际用了多少计算单元、带宽或占用率。

只记住：**H20 执行 CUDA 生态中的设备 kernel。**

停下来回答：本项目的总吞吐能否告诉你某个 Tensor Core 的实际利用率？

---

### 第 6 步：910B4 是 Ascend NPU

910B4 属于 Ascend AI 加速器。模型计算最终由 Ascend 设备算子执行，而不是执行 CUDA kernel。

NVIDIA 文档常用 CUDA core、Tensor Core、SM 等术语；Ascend 使用自己的 AI Core、算子和任务执行体系。两边的硬件单元、指令和调度方式不是一一同名、可直接互换的对象。

只记住：**910B4 不执行 CUDA kernel，它有自己的设备执行体系。**

停下来回答：为 H20 编译好的 CUDA kernel 能否原样放到 910B4 上执行？

---

### 第 7 步：两张卡都有独立的设备内存

模型权重、KV cache、中间张量和编译图所需缓冲区主要放在加速卡的设备内存中。

设备内存不是主机内存。CPU 主机有 225 GiB 内存，不表示 H20 多了 225 GiB 可直接运行 kernel 的显存。

本项目记录了 910B4 的资源型号为 `Ascend910B4-64G`。现有公开证据没有记录 H20 的总物理显存，所以本文不补写一个未经本实验核验的数值。

只记住：**主机内存和设备内存是两套不同资源。**

停下来回答：任务容器显示 125 GiB 主机内存，能否推出 NPU 有 125 GiB 设备内存？

---

### 第 8 步：可用于 KV cache 的内存不等于总设备内存

引擎先加载权重和运行时缓冲区，再把剩余预算的一部分分给 KV cache。

H20 的一次 4B 初始化日志报告：

```text
可用于 KV cache：70.93 GiB
KV token capacity：1,408,320 tokens
按 2,560-token 请求估计最大并发：550.12
```

这些数字属于“4B 模型 + 当次引擎配置”，不是 H20 的硬件规格。

910B4 的一次 27B 初始化日志报告：

```text
可用于 KV cache：5.08 GiB
KV token capacity：27,136 tokens
按 2,560-token 请求估计最大并发：10.60
```

两个例子使用不同模型，不能拿 `70.93 / 5.08` 当作两张卡的显存倍率。

只记住：**引擎报告的 KV 预算取决于模型和配置，不是显存规格表。**

停下来回答：为什么 4B 的 KV 剩余空间不能直接与 27B 的 KV 剩余空间比较硬件？

---

### 第 9 步：主机 CPU 也参与推理

CPU 负责 Python 代码、请求处理、tokenizer、调度、kernel 提交和部分数据处理。

本次任务分配并不相同：

| 部署 | vCPU | 主机内存 | 实验线程设置 |
|---|---:|---:|---:|
| H20 | 20 | 225 GiB | 8 |
| 910B4 | 15 | 125 GiB | 8 |

固定 8 个线程减少了一部分差异，但没有让两台主机完全相同。宿主机共享负载也未完全隔离。

只记住：**这不是只替换加速卡、其余硬件完全不变的实验。**

停下来回答：在线请求延迟是否只受设备计算时间影响？

---

### 第二阶段检查

请区分三个量：

| 量 | 本项目是否完整获得 |
|---|---|
| 设备型号 | 是 |
| 引擎在特定模型下分配的 KV cache | 部分日志中有 |
| 每个 kernel 的计算单元和带宽利用率 | 否 |

因此，不能从总吞吐反推出某个硬件单元的利用率。

## 第三阶段：理解驱动和运行时

### 第 10 步：驱动让操作系统能够控制设备

设备驱动位于操作系统和加速卡之间。它处理设备发现、内存映射、任务提交和错误返回等底层工作。

应用程序通常不直接调用内核驱动，而是先调用用户态运行时。

可以先画成：

```text
Python / C++ 程序
    ↓
用户态运行时
    ↓
内核驱动
    ↓
加速卡
```

只记住：**驱动是操作系统控制设备的底层接口。**

停下来回答：vLLM 是否通常直接绕过运行时去操作 PCIe 设备寄存器？

---

### 第 11 步：CUDA 不只是一个 Python 包

在 H20 路径中，CUDA 软件栈提供设备内存管理、kernel 启动、同步、图执行和编译支持。

PyTorch wheel 名称中的 `+cu129` 表示它面向 CUDA 12.9 构建，但这不等于项目已经记录了宿主机 NVIDIA 驱动的精确版本。

本项目实际记录：

```text
PyTorch 2.13.0+cu129
vLLM 0.30.0+cu129
Transformers 5.17.0
```

只记住：**`cu129` 是构建所面向的 CUDA 版本标记，不是完整驱动清单。**

停下来回答：看到 `torch 2.13.0+cu129`，能否直接写出当时的 NVIDIA 驱动版本？

---

### 第 12 步：CANN 在 Ascend 路径中承担运行时和算子基础设施

910B4 路径使用 CANN 9.1。CANN 包含设备运行、编译和算子相关组件。

为了建立直觉，可以把 CUDA 软件栈与 CANN 都看成“让上层框架使用设备的基础软件”。但两者的组件边界和 API 并不一一对应。

本项目实际记录：

```text
PyTorch 2.10.0+cpu
torch-npu 2.10.0.post4
vLLM / vLLM-Ascend 0.23.0
Transformers 5.5.4
CANN 9.1
```

这里 PyTorch 显示 `+cpu`，不表示模型在 CPU 上推理。Ascend 设备接入由单独的 `torch-npu` 包完成。

只记住：**Ascend 的 PyTorch 设备能力由 `torch-npu` 接入。**

停下来回答：为什么 `torch 2.10.0+cpu` 不能单独证明本次计算落在 CPU？

---

### 第 13 步：上层包、运行时和驱动必须兼容

一个设备函数在编译时和运行时需要遵守同一套二进制接口。这个接口契约常称为 ABI。

早期 910B4 环境出现过：

```text
rtFunctionGetMetaInfoSize
```

相关 ABI 冲突。项目最终选择镜像内匹配的 CANN 9.1 环境后才继续运行。

这类错误不是“模型算慢了”，而是执行链还没有建立成功。

只记住：**版本不兼容时，程序可能在开始测性能之前就失败。**

停下来回答：ABI 符号缺失能否记成 0 tokens/s，然后纳入性能平均值？

---

### 第 14 步：环境变量决定程序找到哪套运行时

Ascend 启动脚本显式设置：

```text
ASCEND_HOME_PATH
ASCEND_CUSTOM_OPP_PATH
LD_LIBRARY_PATH
```

这些变量告诉进程去哪里寻找 CANN 库、自定义算子包和动态链接库。

如果同一镜像里存在多套库，只安装“正确版本”还不够；进程必须实际加载到正确路径。

只记住：**磁盘上存在正确库，不等于进程已经使用正确库。**

停下来回答：为什么改变 `LD_LIBRARY_PATH` 可能改变程序能否启动？

---

### 第 15 步：设备驱动版本仍是本项目的证据缺口

项目保留了框架和主要运行时版本，但公开结果没有完整记录两端内核驱动、固件和微码版本。

因此，本文只能写“CUDA 12.9 构建的软件栈”和“CANN 9.1 软件栈”，不能声称已经完成驱动版本严格对齐。

只记住：**没有采集到的版本必须保留为未知。**

停下来回答：为什么不能根据当前机器的驱动版本，反推历史任务一定使用同一版本？

---

现在应该能读懂两条基础链：

```text
PyTorch/vLLM → CUDA 用户态组件 → NVIDIA 驱动 → H20
```

```text
PyTorch/torch-npu/vLLM-Ascend → CANN → Ascend 驱动 → 910B4
```

箭头表示调用关系，不表示两边组件严格一一对应。

## 第四阶段：理解框架、插件和算子

### 第 16 步：PyTorch 负责表达和调度张量计算

模型代码使用 PyTorch 张量和算子描述计算。

在 H20 路径中，PyTorch 把设备计算交给 CUDA 后端；在 910B4 路径中，`torch-npu` 为 PyTorch 注册 NPU 设备和相应算子。

模型代码相似，不表示最后选择的设备 kernel 相同。

只记住：**PyTorch 是上层计算框架，不是最终设备 kernel 本身。**

停下来回答：同一个 `torch` API 在两种设备上是否一定执行同一份二进制代码？

---

### 第 17 步：vLLM 负责推理引擎层

vLLM 处理模型加载、请求调度、连续批处理、KV cache 管理和生成循环。

它决定“哪些请求在这一轮一起算”“KV block 分给谁”“何时执行 prefill 或 decode”。这些决定会影响吞吐和尾延迟。

只记住：**vLLM 不只是模型的一层包装，它拥有运行时调度状态。**

停下来回答：并发从 8 增到 32 后，性能变化是否可能来自调度器？

---

### 第 18 步：vLLM-Ascend 是设备后端插件

通用 vLLM 核心不能自动知道所有 Ascend 算子、内存约束和图编译方式。

`vLLM-Ascend` 提供 NPU 设备接入、算子实现和编译后端。本次环境中，NPU 图/编译路径使用 `AscendCompiler`。

H20 路径则使用 CUDA 后端，并在相关配置中使用 `torch.compile`、Inductor 和 CUDA Graph。

只记住：**两端的 `combo` 名字相同，底层实现并不相同。**

停下来回答：能否因为两行 CSV 都写 `combo`，就认为两端执行了相同编译器和图机制？

---

### 第 19 步：算子是设备实际执行的计算单元

模型会分解成矩阵乘、归一化、采样、Attention、GDN 等算子。

H20 日志明确记录：

```text
FlashInfer GDN prefill kernel
FlashInfer top-p / top-k sampling
```

910B4 路径则需要 Ascend 对应的 GDN、RMSNorm 和 causal convolution 等算子。

如果关键算子没有设备实现，框架可能失败、回退或换一条执行路径。这三种结果的性能含义完全不同。

只记住：**模型相同，不等于算子实现相同。**

停下来回答：一个后端缺少 GDN kernel 时，能否假设它会自动得到与另一端同等性能的实现？

---

### 第 20 步：自定义算子还需要“能被发现”

910B4 环境中的自定义算子目录起初存在读取权限和加载路径问题。

项目做了三件事：

1. 为容器用户开放只读和目录遍历权限；
2. 设置 `ASCEND_CUSTOM_OPP_PATH`；
3. 把自定义算子的动态库目录加入 `LD_LIBRARY_PATH`。

这些修改使算子可以被加载。它们属于运行门槛，不是吞吐优化。

只记住：**“算子文件存在”和“进程成功注册算子”是两件事。**

停下来回答：修复算子目录权限后程序从失败变为可运行，能否称为 2 倍性能优化？

---

### 第 21 步：Fallback 必须先验证数值，再谈速度

GemmaRMSNorm 路径增加了延迟加载：原生自定义算子可用时走原生路径，不可用时才回退到等价 `torch_npu` 实现。

项目对回退做过窄数值检查：

```text
BF16 最大绝对误差：0.03125
FP16 最大绝对误差：0.00390625
```

这只验证了特定算子的近似一致性，不等于整个模型质量已经由这两个数字证明。

只记住：**fallback 先解决正确执行，再单独检查数值和性能。**

停下来回答：一个 RMSNorm 单测通过，能否直接证明 58,240 条完整请求的语义质量一致？

| 推理引擎 | vLLM | 请求调度、KV cache、生成循环 |

## 第五阶段：理解模型为什么会放大后端差异

### 第 22 步：这个项目不只测普通 Attention 模型

主要测试对象 Qwen3.5 使用 Gated DeltaNet 与 full Attention 混合结构。

项目另测 Qwen3-4B，作为常规 Attention 对照。这样可以观察“硬件优劣是否会随模型结构改变”。

只记住：**Qwen3.5 与 Qwen3 不是完全相同的计算图。**

停下来回答：Qwen3-4B 的结果能否直接替代 Qwen3.5-4B 的结果？

---

### 第 23 步：27B 模型有两类核心层

项目中的 Qwen3.5/3.6/3.8-27B 配置均包含 64 层：

```text
48 层 linear_attention
16 层 full_attention
```

大致每 4 层出现 1 个 full Attention 层。隐藏维度、FFN、头数等配置相同，但 checkpoint 不同。

这里不需要重新学习 Attention。

只记住：**两种核心层会调用不同 kernel，后端覆盖质量因此更重要。**

停下来回答：只优化 full Attention kernel，是否一定覆盖 27B 模型的大多数层？

---

### 第 24 步：模型大小会改变内存余量

模型从 4B 增长到 27B 后，权重占用上升，留给 KV cache 和工作区的设备内存减少。

因此，同一张卡、同一并发数字，在 4B 和 27B 上代表的内存压力不同。

只记住：**并发 32 不是固定的硬件压力单位。**

停下来回答：4B 能稳定并发 32，能否推出 27B 也应稳定并发 32？

---

### 第 25 步：模型系列相同也不能省略 checkpoint 复现

27B 高并发退化在 Qwen3.5、Qwen3.6 和 Qwen3.8 三个 checkpoint 上都出现。

这削弱了“只由某一个 checkpoint 异常导致”的解释，但仍不能证明根因一定在芯片。三者共享相近结构、后端和配置。

只记住：**跨 checkpoint 复现能缩小解释范围，但不能自动定位机制。**

停下来回答：三个 checkpoint 都退化，是否已经排除了调度器或图编译问题？

## 第六阶段：理解 KV cache、block 和并发

### 第 26 步：每条生成请求都需要 KV cache

请求完成 prefill 后，后续 decode 会重复使用历史状态。vLLM 把这些状态放入 KV cache。

请求更长、并发更多或模型更大时，KV cache 压力通常更高。

只记住：**KV cache 是生成阶段的动态设备内存。**

停下来回答：为什么模型权重加载成功，不代表任意并发都能运行？

---

### 第 27 步：vLLM 按 block 管理 KV cache

vLLM 不为每条请求预留一个固定的大连续区域，而是把 KV cache 划分成 block，再按请求进展分配。

可以把它理解成：

```text
设备内存中的 KV 区域
→ block 0
→ block 1
→ block 2
→ ...
```

block 是内存管理单位，不是模型层数，也不是 batch。

只记住：**KV block 是缓存分配单位。**

停下来回答：`block_size=128` 是否表示模型一次只能生成 128 个 token？

---

### 第 28 步：block size 还受后端支持约束

H20 路径可使用其后端支持的默认设置。910B4 初始默认 `block_size=16` 时出现：

```text
No common block size for 16
```

实验随后显式设置：

```text
block_size=128
```

这不是“128 一定比 16 快”，而是当前 Ascend Attention 后端需要双方都支持的 block 大小。

只记住：**block size 先是兼容性契约，然后才可能是性能参数。**

停下来回答：把 16 改为 128 后成功启动，能否据此声称吞吐提高了 8 倍？

---

### 第 29 步：`gpu_memory_utilization` 是引擎预算，不是实际利用率

小模型实验设置：

```text
gpu_memory_utilization=0.88
```

27B 设置：

```text
gpu_memory_utilization=0.92
```

这个参数告诉 vLLM 可把多大比例的设备内存纳入预算。它不是 profiler 测得的“GPU 算力利用率”，也不表示设备始终有 88% 或 92% 忙碌。

参数名在 NPU 路径仍沿用 vLLM 的 `gpu_memory_utilization`，不代表 NPU 变成了 GPU。

只记住：**这是内存预算比例，不是计算单元利用率。**

停下来回答：`gpu_memory_utilization=0.92` 能否证明 AI Core 利用率为 92%？

---

### 第 30 步：`max_num_seqs` 限制调度器同时管理的序列

吞吐扫描主要使用 `max_num_seqs=128`，延迟矩阵主要使用 `max_num_seqs=32`。

它是引擎的调度上限。实际同时运行多少请求还受到请求到达、token budget、KV block 和执行阶段影响。

只记住：**配置上限不等于每个时刻的实际并发。**

停下来回答：`max_num_seqs=128` 是否证明 GPU 每一轮都同时计算 128 条请求？

---

### 第 31 步：并发升高可能增加排队而不是增加产能

在线闭环并发表示系统中最多有多少条在途请求。请求完成一条，再补一条。

如果引擎已经达到某个瓶颈，继续增加并发只会让更多请求等待，导致 TTFT 和 E2E P95 上升。

只记住：**更高并发不保证更高吞吐。**

停下来回答：吞吐不变、P95 上升时，新增加的请求主要发生了什么？

---

### 第六阶段检查

请不要混淆：

| 参数 | 含义 |
|---|---|
| `block_size` | KV cache 的管理单位 |
| `gpu_memory_utilization` | vLLM 可使用的设备内存预算比例 |
| `max_num_seqs` | 调度器管理序列的上限 |
| concurrency | 测试客户端维持的在途请求数 |

它们会互相作用，但不是同一个量。

## 第七阶段：理解两端的优化路径

### 第 32 步：Eager 是最基础的执行路径

`baseline` 使用 eager 路径，并关闭 chunked prefill。每次执行按普通框架路径组织和提交计算。

它提供一个基础参照，但不代表硬件能达到的最佳性能。

只记住：**baseline 是参照，不是理论上限。**

停下来回答：只比较两个 eager 结果，能否证明两个平台优化后的最佳差距？

---

### 第 33 步：编译会把一部分动态图变成优化后的执行方案

H20 路径中的 `torch.compile` 使用 Inductor 等组件分析并编译模型执行片段。

实际日志记录一次 4B 图配置的编译约用 23.65 秒。这个初始化成本不计入稳态吞吐。

NPU 路径使用 `AscendCompiler`。两边都叫“编译”，但编译器和生成的设备程序不同。

只记住：**编译收益与编译初始化成本必须分开测量。**

停下来回答：稳态吞吐提高时，能否推出第一次请求也一定更快？

---

### 第 34 步：Graph 减少重复调度开销

H20 会捕获 CUDA Graph，再重复 replay。NPU 路径由 Ascend 后端采用自己的图/编译机制。

Graph 不是缓存模型答案。每次 replay 仍然根据当前输入执行计算。

两端 `graph` 配置的目标相似，但底层机制不同，所以不能把收益差直接解释成芯片差。

只记住：**Graph 复用执行安排，不复用输出答案。**

停下来回答：CUDA Graph 能否直接在 910B4 上原样 replay？

---

### 第 35 步：Chunked prefill 改变长输入的调度粒度

Chunked prefill 把较长输入拆成若干 token 块，与 decode 请求共享调度预算。

它可能改善混合负载下的调度，但会增加切块和调度成本。本项目固定长度离线负载中，它没有提高 4B 吞吐。

只记住：**解决调度问题的优化，不一定提高每一种吞吐微测。**

停下来回答：chunked prefill 在一组实验中变慢，能否证明它在在线混合请求中永远无用？

---

### 第 36 步：Prefix cache 只对共享前缀有意义

如果多条请求拥有完全相同的前缀，prefix cache 可以复用前缀计算。

普通性能请求加入唯一标识，避免实验无意中测到共享前缀收益。只有专门的缓存消融才构造共享前缀。

只记住：**没有共享前缀，就没有可复用的前缀计算。**

停下来回答：普通随机请求上的 prefix cache 结果能否代表固定 system prompt 的业务？

---

### 第 37 步：FP8 改变数值格式和 kernel 路径

H20 4B 实验验证了即时 FP8 量化路径。在 1K→128、batch 32 下：

```text
graph：1,524 output tok/s
FP8：  1,986 output tok/s
```

910B4 没有完成对应 FP8 测量。空缺表示“未测”，不表示收益为零。

只记住：**跨硬件比较一个优化前，必须两端都有对应证据。**

停下来回答：能否用 H20 的 FP8 结果与 910B4 的 BF16 结果证明纯硬件优势？

---

### 第 38 步：MTP 的接受率不等于最终加速比

MTP 会提出多个候选 token，再验证能接受多少。

日志中的接受率约为 67% 到 76%，但 4B、batch 32 的 MTP 吞吐没有稳定超过 graph。提出、验证和调度都有成本。

只记住：**多接受 token 只是中间指标，最终仍要看端到端吞吐和延迟。**

停下来回答：接受率 75% 是否自动意味着吞吐提高 75%？

---

### 第 39 步：`combo` 不保证比最佳单项更快

项目把图/编译路径与 chunked prefill 的组合称为 `combo`。

4B、1K→128、batch 32 的结果：

| 配置 | H20 tok/s | 910B4 tok/s |
|---|---:|---:|
| baseline | 647 | 526 |
| graph | 1,524 | 855 |
| chunk 2048 | 628 | 495 |
| combo | 1,484 | 824 |

两端的 `combo` 都没有超过 graph 单项。

只记住：**优化项会相互作用，收益不能直接相加。**

停下来回答：graph 提高 30%、chunk 提高 10% 时，combo 是否必然提高 40%？

---

### 第七阶段检查

你应该能解释：

```text
同名优化 ≠ 同一底层实现
多个优化打开 ≠ 收益相加
稳态更快 ≠ 初始化更快
中间指标更好 ≠ 端到端一定更快
```

## 第八阶段：理解实验矩阵和指标

### 第 40 步：第一套实验测饱和吞吐

吞吐主矩阵包含：

```text
2 种硬件
× 5 个模型
× 2 种配置
× 2 种输入长度
× 3 种输出长度
× 4 种 batch
= 480 格
```

一格是一种唯一配置，不是一条请求。加上重复、确认和消融后，底层共有 1,326 次吞吐测量。

只记住：**480 是配置数，不是请求数。**

停下来回答：一格中能否包含 64 条请求和 3 次重复？

---

### 第 41 步：第二套实验测请求级延迟

请求级矩阵记录每条请求的 token 到达时间：

```text
728 格
58,240 条成功请求
```

它包含离线异步和本机流式 HTTP 路径，用于观察 TTFT、TPOT 和 E2E。

只记住：**吞吐矩阵和请求级延迟矩阵回答不同问题。**

停下来回答：只有总 output tok/s，能否知道第一个 token 何时到达？

---

### 第 42 步：TTFT 观察首 token

```text
TTFT = 第一个可观察 token 到达时间 - 请求开始时间
```

它包含排队、prefill、调度和调用链开销。

只记住：**TTFT 回答“多久开始看到答案”。**

停下来回答：TTFT 低能否证明完整答案也最早完成？

---

### 第 43 步：TPOT 观察后续生成速度

输出 token 数为 \(n>1\) 时：

```text
TPOT = (最后 token 时间 - 第一 token 时间) / (n - 1)
```

TPOT 越低，首 token 之后平均生成越快。

只记住：**TPOT 不包含等待第一 token 的全部时间。**

停下来回答：只有 1 个输出 token 时，是否有可定义的 TPOT？

---

### 第 44 步：E2E P95 观察尾部完整等待

E2E 是一条请求从开始到完成的总时间。

P95 表示约 95% 的样本不高于这个值。它不是最大值，也不是生产 SLA。

只记住：**E2E P95 回答“大多数慢请求要等多久完成”。**

停下来回答：P95 为 10 秒是否表示每一条请求都在 10 秒内完成？

---

### 第 45 步：在线闭环并发和离线 batch 不是同一个量

离线 batch 是一次提交的一组请求。在线闭环 concurrency 是客户端维持的在途请求上限。

它们都影响并行度，但调度过程和计时范围不同，不能直接把 `batch=32` 与 `concurrency=32` 当成同一个实验。

只记住：**数字相同，不表示负载协议相同。**

停下来回答：离线 batch 32 的 tok/s 能否直接替代在线并发 32 的 E2E P95？

---

### 第八阶段检查

看到一个性能数字时，至少先问：

```text
哪个模型？
输入和输出多长？
BF16 还是 FP8？
baseline、graph 还是 combo？
离线 batch 还是在线并发？
吞吐、TTFT、TPOT 还是 E2E？
```

缺少这些条件，倍率几乎不能复用。

## 第九阶段：一步步读懂主要结果

### 第 46 步：先读固定场景，不先找总冠军

固定为在线闭环、并发 32、1K 输入、128 输出、`combo`：

| 模型 | H20 output tok/s | 910B4 output tok/s | H20 / 910B4 |
|---|---:|---:|---:|
| Qwen3.5-2B | 3,189 | 1,567 | 2.03x |
| Qwen3.5-4B | 1,413 | 757 | 1.87x |
| Qwen3.5-9B | 842 | 561 | 1.50x |
| Qwen3-14B | 468 | 404 | 1.16x |

在这个固定长输出场景中，H20 吞吐更高。

只记住：**这是一个条件完整的直接观察，不是所有任务的总排名。**

停下来回答：这张表能否推出 910B4 在单 token 判断中也一定更慢？

---

### 第 47 步：短输出给出了反例

同样在在线 `combo`、1K 输入、并发 32 下：

```text
9B，1 token：
910B4 9.96 req/s
H20   9.13 req/s

14B，1 token：
910B4 7.09 req/s
H20   4.84 req/s
```

输出很短时，prefill、首 token 和调度占比更高，结果方向可以改变。

只记住：**一个有效反例就足以否定“H20 所有场景都更快”。**

停下来回答：2B 长输出的 2.03x 能否覆盖 14B 单 token 判断？

---

### 第 48 步：首 token 和完整生成也会给出不同答案

9B、1K→128、`combo`、在线并发 32：

| 指标 | H20 | 910B4 | 较优 |
|---|---:|---:|---|
| TTFT P95 | 3.20 s | 3.10 s | 910B4 略低 |
| E2E P95 | 6.40 s | 8.41 s | H20 |
| 请求吞吐 | 6.58 req/s | 4.38 req/s | H20 |

910B4 稍早给出第一 token，H20 更早完成整条 128-token 响应。

只记住：**“开始得快”和“完成得快”不是同一个指标。**

停下来回答：聊天产品只关心首屏响应时，是否应只按 output tok/s 排名？

---

### 第 49 步：27B 的问题是“并发越高反而越慢”

910B4、1K→128、`combo`：

| 模型 | 并发 8 tok/s | 并发 32 tok/s | E2E P95：8 → 32 |
|---|---:|---:|---:|
| Qwen3.5-27B | 97.8 | 49.0 | 10.26 s → 101.65 s |
| Qwen3.6-27B | 97.4 | 48.9 | 10.36 s → 102.00 s |
| Qwen3.8-27B | 97.3 | 48.8 | 10.32 s → 102.17 s |

并发从 8 增至 32 后，吞吐约减半，尾延迟约放大到 10 倍。

只记住：**这是已复现的部署现象。**

停下来回答：并发提高 4 倍后，吞吐是否提高了？

---

### 第 50 步：现有数据没有定位 27B 退化根因

可能需要检查的方向包括：

- KV block 压力和是否发生抢占；
- scheduler 的排队与批组成；
- Ascend 图编译对不同 shape 的行为；
- GDN 或其他算子的高并发效率；
- 主机提交和同步；
- 设备内存带宽与实际 kernel 时间。

但项目没有采集完整 profiler、调度事件和设备内存时间线，所以这些都只是待验证假设。

只记住：**观察到退化，不等于已经知道退化机制。**

停下来回答：能否把 27B 退化直接写成“910B4 的 KV cache 有缺陷”？

---

### 第 51 步：运行修复不能记作性能收益

910B4 为成功运行做过：

```text
CANN 9.1 环境对齐
自定义算子路径和权限修复
block_size=128
GemmaRMSNorm 加载与 fallback
```

它们解决的是 ABI、注册和兼容性问题。没有“修复前的有效性能基线”，所以不能计算修复带来的加速比。

只记住：**从失败到成功叫可运行性修复，不叫性能加速。**

停下来回答：程序修复前无法完成一条请求，是否存在可用于计算加速比的有效分母？
